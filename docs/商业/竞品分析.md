# 《盟书 PactBook》竞品分析报告
**版本**：v2.0（按新定位重写：婚恋信任基础设施） | **状态**：定稿
**关联文档**：MRD v1.1、PRD v1.0、SRS v1.0
---
## 一、竞品分层与选择逻辑
**按新定位（陌生人公示 + 关系陈述 + 机构API + 双区架构），市场不存在完全对位的直接竞品，竞争压力来自三层：** ①功能部分重叠的关系记录类产品；②可能推出婚恋场景的通用存证工具；③服务同一批B端客户（婚恋机构）且可能自建信任背书能力的SaaS服务商。
分析框架采用三维评估：**信任背书能力（能验证什么）、数据主权归属（数据在谁手里）、商业模式兼容性（能否长期不牺牲中立性）**。
| 竞品层 | 判断标准 | 本层结论 |
|---|---|---|
| **第一层·直接竞品** | 做关系记录/合约/公示且带信任背书功能 | 功能部分重叠，但无一同时具备"双边签认+密码学存证+零存储+用户主权公示" |
| **第二层·间接竞品** | 通用存证工具、关系维护app、情侣社交 | 与盟书互补大于竞争，但占据用户心智与时间 |
| **第三层·潜在进入者** | 有用户/数据/资金优势，可快速切入信任赛道 | **真正威胁所在**：婚恋巨头、职场认证玩家、B端SaaS |
下文每个竞品给出统一维度的模块卡：**产品定位 → 核心功能 → 信任/存证机制 → 与盟书的重叠与差异**。

## 二、第一层：直接竞品（关系记录/公示类）
### S1 糖果日记
**产品定位**：中国市场的"合约恋爱+社交征信"先行者，2019年11月上线，运营方为上海共情网络科技。
**核心功能**：恋爱合约签署、爱情小法庭（纠纷AI裁决）、社交信用分体系、人脸识别实名。
**信任/存证机制**：人脸识别实名 + 平台自建"社交信用分"——对"违背合约"的用户扣分并限制交友功能。
**与盟书的重叠与差异**：
- 重叠：都做"关系合约"概念，都有实名
- 差异（三点致命）：① 糖果日记是**评分体系**（盟书红线：系统不做人品评审）；② 数据存于平台服务器（盟书Vault零存储）；③ 无密码学存证与司法锚定，合约只是UI呈现而非法律证据。糖果日记把"人际信任商品化"做成社交平台，盟书做的是"事实存证"工具。
### S2 小盟约
**产品定位**：基于以太坊的"爱情誓言"签署工具，个人/小团队开发。
**核心功能**：双方在线签署誓言，签署后不可篡改，仅双方可见。
**信任/存证机制**：以太坊智能合约上链。
**与盟书的重叠与差异**：
- 重叠：都有"上链不可篡改"概念，都只对签署行为负责
- 差异：① 小盟约上链的是**誓言内容**（即使加密也是内容上链，存在隐私暴露面），盟书只上链**加盐哈希**；② 小盟约是单点工具（签完即走），无关系生命周期管理（关闭协议、完整性宣誓）；③ 无司法链锚定，公有链在国内的证据采信度弱于至信链/天平链；④ 产品成熟度低，疑似停滞。**小盟约验证了概念可行，也示范了"只做誓言工具"做不深。**

## 三、第二层：间接竞品（通用工具与关系维护类）
### S3 腾讯电子签（最强替代品威胁）
**产品定位**：腾讯旗下的通用电子合同签署平台，C端个人版支持借条/收据/合同，免费使用。
**核心功能**：微信原生人脸核身、至信链区块链存证、小程序一键发起签署。
**信任/存证机制**：至信链锚定 + 微信核身 + 司法判例背书。
**与盟书的重叠与差异**：
- 重叠：都提供"实名签认 + 至信链锚定"，用户拿腾讯电子签同样可以签一份恋爱协议
- 差异：① 腾讯电子签是**通用合同工具**——用户自己起草条款、自己理解法律含义；盟书是**关系专用工具**——字段、仪式、关闭流程、完整性宣誓全部为关系场景预设计；② 腾讯电子签**明文合同存于腾讯服务器**，盟书Vault零存储；③ 腾讯电子签没有公示、机构API、关系陈述这些"关系场景"层
- **威胁应对**：不硬刚，主动接入至信链生态做垂直深耕；真正的护城河是"关系专用场景理解"而非底层签名技术
### S4 Paired（关系维护订阅制的标杆）
**产品定位**：英美市场的情侣关系维护App，2020年10月上线，累计下载800万，Apple App of the Day（2024年1月）。
**核心功能**：每日问题、情侣问答解锁、纪念日追踪、关系科学测验、专家内容，每天5分钟。
**信任/存证机制**：无。纯互动与内容产品，不涉及任何存证。
**与盟书的重叠与差异**：
- 重叠：服务对象相同（认真关系中的情侣），都占据"关系"心智
- 差异：① Paired做**关系质量**（沟通、亲密度），盟书做**关系事实**（发生过、谁签了、何时关闭）——完全互补，理论上一对情侣可以同时用两个；② Paired是订阅制（$14.99/月或$40-75/年），验证了"为关系付费"意愿成立，盟书的C端免费策略在这个验证基础上是降维打击；③ Paired无B端、无公示、无跨关系档案
- **战略启示**：Paired证明情侣愿意为关系投入时间与金钱，但盟书的裂变逻辑（互证即双用户）与Paired的拉新逻辑（单用户邀请伴侣）不同——盟书的K系数天然更高
### S5 Between（情侣社交的存续标杆）
**产品定位**：韩国VCNC开发的情侣私密社交App，累计下载超3500万。
**核心功能**：双人聊天、共享相册、纪念日、留言板——关系的"相册"。
**信任/存证机制**：无。
**与盟书的重叠与差异**：
- Between记录**感受与回忆**（照片、聊天），盟书记录**事实与承诺**（签署、关闭、宣誓）；Between是关系的"相册"，盟书是关系的"公证处"。互补关系，Between的用户群是盟书的潜在转化池。
### S6 婚恋门店管理系统/红娘CRM（B端潜在竞合，最微妙的一层）
**产品定位**：服务婚恋机构的SaaS系统，代表玩家包括初告文化（38城门店）、百合佳缘集团、珍爱网、我主良缘、有缘网。2023年国内婚恋服务市场规模突破千亿元，数字化系统渗透率年均提升12%。
**核心功能**：会员资料管理、智能匹配引擎、红娘工作台、活动排期、财务对账、客户跟进全流程。
**信任/存证机制**：实名认证审核 + 企业自建信用体系。以初告文化为例：身份证/学历/工作认证、敏感数据脱敏、等保二级、操作日志留痕。
**与盟书的重叠与差异（竞合关系，最需警惕）**：
- **合作面**：盟书场景B（现场授权传输）的**目标客户就是这批系统**——机构想接入盟书API获取用户授权档案
- **竞争面**：这批SaaS已有自建认证体系（学历、工作、实名），若某头部SaaS决定自建"关系经历存证"模块（比如在CRM里加"历史关系核验"字段），就是垂直竞品
- **盟书的结构优势**：SaaS自建的是**机构内私有数据**，无法跨机构流通（用户在A机构的记录，B机构查不到）；盟书是**用户自持的跨机构信任资产**——用户换机构，档案跟着走。这个差异是盟书对B端谈判的核心筹码："接入我，你的客户带档而来；不接入，你的数据是孤岛"
- **威胁等级**：中。触发条件是某头部SaaS获客压力大到必须做差异化，才可能自建；更可能的路径是他们选择接入盟书而非自建（开发成本 vs API接入成本）

## 四、第三层：潜在进入者（真正威胁所在）
### S7 BOSS直聘"看准"App（职场婚恋新玩家，2024年最新动向）
**产品定位**：BOSS直聘旗下婚恋App"而立"于2024年9月更名为"看准"，定位"严肃靠谱的职场人婚恋平台"。
**核心功能**：实名/学历/头像/工作四重认证，工作认证需企业微信/钉钉名片、社保、工牌等证明；每天随机展示10位用户卡片。
**信任/存证机制**：**工作信息认证**——用职场身份为婚恋信任背书。
**与盟书的重叠与差异**：
- 重叠：都在解决"婚恋信任"问题，都依赖强认证
- 关键差异：看准认证的是**当前职业身份**（"我在这家公司工作"），盟书认证的是**历史关系行为**（"我曾如何开始、如何结束、对方如何评价我"）——前者证明"你是谁"，后者证明"你做过什么"。两个维度完全正交，理论上互补
- **战略信号**：BOSS直聘放弃职场点评、转战婚恋，说明大厂已看到"职场数据+婚恋信任"的变现路径。若"看准"婚恋跑通，下一步完全可能扩展到"历史行为认证"——**这是中期最需要盯的对手**。但看准的路径依赖是B端（企业认证），做C端关系存证需要架构重构（从机构数据源转向用户主权），转身成本不低
### S8 看准网（已倒闭，历史教训库）
**产品定位**：中国最大公司评价平台，6000万会员，运营12年后于2024年9月30日停止服务。
**倒闭原因**（对盟书陈述模块的直接警示）：
- **商业模式根本矛盾**：主要收入依赖BOSS直聘的企业客户，又必须在看准网展示影响企业形象的负面评价——2020年删除"评价"功能，抛弃初衷
- **匿名评价失真**：匿名导致刷好评、不实差评泛滥，企业被一条差评拖垮招聘却无从申诉
- **台湾对比样本**：台湾"比薪水"以匿名+人工审核+积分互助的良性循环存活下来
**对盟书的启示（三条）**：
1. 盟书陈述模块**绝不匿名**——实名+关系存证绑定是根本差异化（评价者身份→关系存在性→内容三者哈希关联，追责链完整）；
2. 盟书的商业模式**不向"被评方"收任何钱**——不存在"花钱删差评"的动机结构，中立性的经济基础比道德承诺更可靠；
3. 台湾"积分互助"模式验证了**贡献换查阅**的良性循环可行，盟书的数据分红机制（被查询获收益）是其在关系场景的变体。
### S9 百合佳缘/珍爱网（婚恋巨头）
**产品定位**：传统婚恋巨头，20年品牌，庞大用户库。
**核心功能**：线上匹配 + 线下红娘门店（百合佳缘旗下世纪佳缘等）。
**信任/存证机制**：平台实名认证 + 自建会员信用体系。
**与盟书的重叠与差异**：
- 巨头做的是**撮合生意**（让用户配对成功），盟书做的是**信任基础设施**（让事实可验证）——撮合平台理论上可以接入盟书API增强用户信任度，而非竞争
- 巨头若自建"关系经历认证"：动机弱（用户在自家平台的关系历史本身就是自有数据，无需第三方）、能力存疑（密码学与司法存证非其技术栈）、且与其"促成交"KPI冲突（关系关闭记录对撮合平台是负资产叙事）
- **威胁等级**：低-中。更可能的终局是被巨头投资/收购（参考Couple被Life360收购的先例）

## 六、差异化机会点（新定位下的空白市场）
综合三层竞品，盟书的空白定位可归纳为三句话：
1. **"用户自持的跨机构信任资产"**——对红娘CRM（S6）：他们的数据是机构私有孤岛，盟书的档案跟着用户走。这是B端谈判的核心筹码，也是巨头难以复制的结构性差异（巨头的数据是平台的，不是用户的）。
2. **"实名+存证绑定的评价体系"**——对看准网教训（S8）：匿名评价死于商业模式冲突与内容失真；盟书陈述模块以实名+关系存证+双向并列+数据分红构建了完全不同的经济结构——**被评方是数据分红的受益人而非受害者**，利益方向逆转。
3. **"历史行为认证"这一正交维度**——对看准App（S7）：职场婚恋平台认证"当前身份"，盟书认证"历史行为"，两者天然互补；中期若看准婚恋跑通，接入盟书API是它增强信任深度的最短路径——**把潜在对手变成渠道**。

## 七、威胁应对策略
| 威胁 | 触发情景 | 应对 |
|---|---|---|
| 腾讯电子签推出婚恋模板 | 中概率，腾讯有场景嗅觉 | 不硬刚——主动接入至信链生态，把"关系专用场景理解"做成护城河；保留被投资/收购选项 |
| 红娘CRM头部自建关系认证模块 | 中概率，B端获客压力驱动 | 打时间差：抢先签约2-3家种子机构（以场景B免费通道切入），建立"跨机构档案"网络效应——机构接入越多，自建成本越不划算 |
| 看准App扩展到历史行为认证 | 中期概率，取决于其婚恋业务跑通 | 转化为渠道：主动向其输出API（盟书的信任基础设施+看准的流量入口）；同时加快C端档案积累构筑数据壁垒 |
| 婚恋巨头下场 | 低概率，与其KPI冲突 | 维持中立基础设施定位，撮合平台的信任后端是其最优选择而非竞品 |

## 八、中长期视角：真正的对手会是谁
短期（1年内）没有直接竞品，最大的敌人是**市场教育**——用户尚未被训练出"关系事实需要存证"的认知。
中期（2-3年）的对手是**腾讯电子签的场景化延伸**与**看准App的信任维度扩展**，盟书的窗口期在于C端档案积累的网络效应：每多一段双签关系，多一份公示档案，后来者的冷启动成本就高一分。
长期看，最可能的终局不是被竞品击败，而是**被生态吸收**——成为婚恋产业（巨头、SaaS、婚介机构）普遍采用的信任底层协议，以开源与中立性作为不被单一生态吞噬的锚。这与Couple被Life360收购、Between独立存续的两种路径对照：盟书选择第三条路——**做协议而非产品，做基础设施而非应用**。
