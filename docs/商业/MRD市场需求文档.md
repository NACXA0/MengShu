## 1. 执行摘要

**盟书（TrustBook）是一个双边签认、密码学存证、开源（MIT）的关系事实基础设施。**
产品逻辑建立在一个双向社会需求上：

> **认真恋爱的人，希望关系是公开且可被证明的；寻找关系的人，希望了解对方的真实经历。**

- **C端**：个人免费使用（永久），核心是“Vault区”的双边互证仪式——两人的关系事实经双方实名签认、哈希上链，成为不可篡改、可司法出证的记录；
- **公示体系（Plaza区）**：用户自愿将档案摘要挂出，陌生人可查、可随时关闭；
- **B端**：婚恋机构通过两条合规通道获取信息——批量查询公开信息（付费API）、本人现场授权传输（免费通道+机构系统对接）；
- **营收模式**：开源软件 + C端免费 + B端API付费 + 非定向品牌广告 + 自愿捐赠；
- **核心卖点唯一且不可妥协：可信。**

## 2. 市场背景与驱动因素

### 2.1 结构性背景

| 驱动因素 | 说明 |
|---|---|
| **信任供给短缺** | 婚恋市场信息不对称是存量痛点：婚史隐瞒、并行关系、经历造假导致的纠纷高发，现有平台“实名认证”只能证明“人是真的”，不能证明“经历是真的” |
| **诈骗治理刚需** | “杀猪盘”类犯罪的本质是身份与人设的完全虚构；多轮双边签认的关系签名链在密码学上不可伪造，是结构性反诈基础设施 |
| **政策框架成熟** | 《个保法》确立“知情-同意”与数据流通框架；《数据二十条》鼓励个人数据有偿授权使用——“本人授权、有偿流通”是政策鼓励方向 |
| **技术设施现成** | 电子签名、区块链司法存证（至信链/天平链）、可信时间戳均已获司法背书，可信基础设施无需自建 |
| **社会观念迁移** | 年轻一代对“经历透明”的接受度上升；“体面的分手记录”正在从羞耻转变为个人信用资产 |

### 2.2 时机判断

## 为什么是现在：① 婚恋平台信任危机频发，市场对第三方可信验证的付费意愿被反复教育；② 司法链存证的证据效力已有大量判例支撑；③ 开源信任工具在国内尚无先例，先发者定义品类。

## 3. 市场规模（框架，数字待委托调研补充）

| 层级 | 定义 | 备注 |
|---|---|---|
| TAM | 中国婚恋市场年交易规模 + 个人征信/存证服务市场中“个人信任”相关部分 | 需委托数据源 |
| SAM | 处于认真婚恋阶段、愿意为可信验证付费/公示的人群 × 婚恋机构核验服务支出 | 核心变量：公示意愿率 |
| SOM | 首年：1-3家种子婚恋机构API合作 + 自然增长的C端公示用户 | 验证付费模型为第一目标 |
**关键假设（待验证）**：

- H1：认真关系中的双方愿意进行互证仪式（转化率假设 ≥5% 的深度用户）；
- H2：经历清白者愿意公开公示（公示率假设 ≥15%）；
- H3：婚恋机构愿意为合规授权查询付费（客单价假设：按次1-10元区间）。

## 4. 目标客群与需求分析

### 4.1 C端客群

| Persona   | 特征                | 核心需求                            | 对应功能           |
| --------- | ----------------- | ------------------------------- | -------------- |
| **认真恋爱者** | 18-35岁，期望恋爱者      | 关系被郑重记录、防对方抵赖、给关系一个“仪式”         | Vault双签互证、仪式凭证 |
| **经历优越者** | 关系史清白、多段和平关闭      | **让“可信”变成择偶竞争力**，反向筛选出同样在意诚实的对象 | Plaza公示、陈述证言   |
| **重回市场者** | 结束一段长期关系后再次进入婚恋市场 | 快速自证清白，省去反复解释                   | 公示页/现场授权一键出示   |
| **求证者**   | 正在了解潜在对象          | 在对方自愿展示的前提下了解其经历                | 公开页查询、扫码验证     |

### 4.2 B端客群

| 客群 | 场景 | 付费方式 |
|---|---|---|
| **婚恋机构（核心）** | 红娘门店：客户到店后现场授权，结构化资料直接进入机构CRM，替代手工誊抄 | 系统对接费 + 批量查询套餐 |
| **婚恋平台** | 线上平台对入驻用户做自愿公示核验 | 批量查询API |
| **婚前咨询/心理机构** | 经授权调取关系档案做辅导参考 | 单独合作模式 |

### 4.3 需求汇总表

| 编号 | 需求 | 客群 | 优先级 | 验证状态 |
|---|---|---|---|---|
| R1 | 认真的关系希望被公开、可证明 | C-认真恋爱者 | P0 | 待深访验证 |
| R2 | 寻找关系者希望了解对方经历 | C-求证者 | P0 | 待深访验证 |
| R3 | 经历清白者希望可信成为竞争力 | C-经历优越者 | P0 | 待深访验证 |
| R4 | 机构需要真实可验、合规授权的数据源 | B-机构 | P0 | 待BD访谈验证 |
| R5 | 机构需要现场数据结构化入系统 | B-机构 | P1 | 场景B API |
| R6 | 被查者要求知情、有偿、可撤 | C-全体 | P0 | 法定义务 |
| R7 | 平台需可持续营收支撑开源运营 | 运营约束 | P0 | 本MRD商业模式 |

## 5. 竞争格局（摘要，详见竞品分析报告）

| 结论 | 内容 |
|---|---|
| 直接竞品 | **空缺**。糖果日记（有信用分，违背中立）、小盟约（无司法锚定）、Promise（行为打卡）均不构成同位竞争 |
| 最大威胁 | 腾讯电子签若推出婚恋场景模板。对策：**接入其存证生态做垂直深耕**，把最大威胁转化为基础设施盟友 |
| 反面教材 | 恋爱合约（无效合同判例）、爱情银行（现金激励崩盘）→ **产品永不引入金钱兑付型承诺** |
**差异化一句话**：糖果日记卖“信用分”，腾讯电子签卖“合同工具”，盟书只做一件事——**双边签认的事实存证，以及用户主权之下的合规流通**。

## 6. 产品定位与价值主张

- **一句话定位**：双边签认、密码学存证、开源免费的关系信任基础设施。
- **对C端**：“你交给某个人的秘密（Vault），和挂出来卖的招牌（Plaza），永远分开。”
- **对B端**：“我们不给你们独家信息，我们给的是**用户自愿展示、每一条都带司法级存证凭证、随时可撤回**的公开信息。”
- **对监管**：“个人数据授权流通的合规样板：知情、同意、可撤、留痕；平台不以查询运营费变现。”
**灵魂红线（写入公司章程级）**：Vault区数据不向任何第三方输出，任何商业模式不在此开缝。

## 7. 商业模式【v2.1 修订：零平台运营费】

```
付费边界（硬约束）：
├─ 盟书不收取任何平台运营费（查询费 / 接口开通费 / 套餐 / C 端核心功能费）
└─ 全平台唯一付费项：支付宝「身份验证」
    （开放平台按次计费；产品说明：
     https://open.alipay.com/api/detail?code=I1080300001000044085&index=1
     ——是身份验证，不是「人脸核验」产品命名）

可持续支撑（非向用户强制收费）：
├─ 自愿捐赠（锚定、审核、托管）
├─ 机构可自建锚定节点（MIT 开源）
└─ 可选非定向品牌展示（非用户付费项，另循广告法）

成本结构：
├─ 锚定服务费（至信链/天平链，Merkle 批量摊薄；捐赠不足则降频）
├─ 支付宝身份验证按次计费（唯一外部付费账单）
├─ 内容审核（Plaza 陈述定向小量）
└─ 开源社区维护
```

## **开源与可持续的关系**：客户端与协议 MIT 开源，任何机构可自建锚定节点；官方托管靠捐赠与自建，**不以运营费变现**。**开源不是情怀，是获客与公信力策略**——代码可审计本身就是“可信”卖点的一部分。
**数据分红**【v2.1 暂停】：原「查询费 30% 分成」依赖平台向机构收费；现零运营费，分红无基数，暂停对外承诺。

## 8. 法规合规要求（本MRD核心章节）

### 8.1 总体法律定性

产品是**个人信息处理者 + 电子存证技术服务提供者**，因涉及Plaza公示与机构API，**不再主张“与婚恋无关”**，主动按“婚恋信任基础设施”的高标准合规，不作监管套利。

### 8.2 分场景合规义务

| 场景 | 法律依据 | 平台义务 |
|---|---|---|
| Vault双签存证 | 个保法28-30条（敏感信息单独同意）、电子签名法 | 上链前单独同意弹窗、哈希加盐、可删除（墓碑机制） |
| Plaza公示 | 个保法25条（公开需单独同意） | Opt-in默认关闭、字段自选、一键撤回、撤回后API数据失效 |
| 关系陈述 | 民法典1195-1197、网络信息内容生态治理规定 | 资格核验（绑定存证关系）、双向并列、答辩权、通知-删除通道、定向审核 |
| 场景A批量查询 | 个保法27条（已合法公开信息，“明确拒绝除外”） | 用途限定合同、禁止缓存转售条款、查询留痕、撤回失效机制、数据分红 |
| 场景B现场授权 | 个保法23条（提供第三方六要素告知+单独同意）、29条（敏感信息叠加同意） | 授权弹窗六要素、传输凭证留痕、告知“机构为独立处理者”、删除权协助通道 |
| 广告 | 广告法 | 非定向投放、行业白名单（婚恋可、金融医疗游戏拒） |

### 8.3 资质清单

ICP备案与许可、EDI（在线数据处理交易）许可、区块链信息服务备案（网信办）、算法备案（如涉及推荐）、内容审核团队资质、等保二级起步。

### 8.4 法律风险总评

| 场景 | 风险等级 | 剩余风险说明 |
|---|---|---|
| Vault存证 | 低 | 架构性规避（零存储+匿名化） |
| 现场授权传输 | **低（全产品最低）** | 本人完全在场、六要素告知、实时勾选 |
| 批量公开查询 | 低-中 | 取决于“撤回即失效”的执行力度；需合同+技术双保险 |
| 关系陈述 | 中 | 实名+存证绑定使追责链完整（优于看准网模式），但公开内容属性决定审核义务不可免除 |

## 9. 市场进入与裂变策略

### 9.1 裂变引擎（产品自增长逻辑）

```
核心闭环：
认真的关系 → 互证仪式（双用户同時入网，K系数天然>1）
     ↓
关系终止 → 双签和平关闭 → 档案积累"体面记录"
     ↓
重回市场 → 挂出Plaza招牌（可选有分红）→ 被查询获收益
     ↓
求证者验证 → 发现可信者的价值 → 期待自己也拥有 → 入网
```

**双重需求互为镜像**：R1（想证明的人）和R2（想了解的人）是同一市场的两侧，公示者越多，求证者的验证行为越有价值；求证行为越普遍，公示者的“可信资产”越值钱——**网络效应建立在信任本身上**。

### 9.2 进入节奏

| 阶段 | 动作 | 目标 |
|---|---|---|
| Phase 1（0-6月） | Vault功能上线，开源发布，种子社群（关注隐私/开源/亲密关系的垂直社区） | 验证H1，积累1000次互证 |
| Phase 2（6-12月） | Plaza公示+关系陈述上线；开放公开页 | 验证H2，公示率≥15% |
| Phase 3（12-18月） | 场景B机构对接（1-3家种子红娘门店），场景A API灰度 | 验证H3，跑通付费闭环 |
| Phase 4（18月+） | 广告位（非强制付费）开放、行业联盟公约 | 信任基础设施定型；仍不恢复平台运营费 |

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 公示成为机构隐性门槛（软强制） | **高** | 数据分红+随时撤回+查询透明；监测公示率与撤回率，若机构普遍要求公示则推动行业公约“未公示不得歧视” |
| 陈述模块引发名誉权纠纷 | 中 | 定向审核+通知删除+实名追责威慑 |
| 腾讯电子签下场做婚恋模板 | 高 | 深度接入其生态；保留被投资/并购选项 |
| 机构超范围使用数据 | 中 | 合同违约金+审计权+黑名单机制+吊销API资质 |
| “经历优越者”噱头化导致反噬 | 中 | 严格中立文案基线：不出现“清白”“诚信分”等词，公示页不加任何价值排序 |
| 开源模式营收不足 | 中 | 锚定降级机制（实时→每日批处理）；B端优先原则 |
