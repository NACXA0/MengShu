# 贡献指南 | Contributing to PactBook

感谢你考虑为盟书做贡献。这份指南很短，因为我们的规则也很少——但每一条都是硬的。

---

## 0. 先读：灵魂红线（PR 门禁）

本项目的全部价值建立在一个架构事实上：

> **Vault 区数据向第三方的输出 = 0 字节。**

任何 PR，无论功能多好、代码多漂亮，触碰以下任一条即被直接关闭：

| # | 红线项 |
|---|---|
| R1 | 引入任何把 Vault 明文、SM2 私钥或盐传出设备的代码路径（**含调试日志、崩溃上报、埋点字段**） |
| R2 | 裸哈希上链或入库（所有摘要必须 HMAC-SM3 加盐构造） |
| R3 | SM4 ECB 模式、自定义 SM2 曲线参数、非硬件 TRNG 随机源 |
| R4 | 用户画像、设备指纹、跨站追踪、定向广告代码 |
| R5 | 评分、排行、匹配、推荐逻辑（无论命名多么"中性"） |
| R6 | 服务端 schema 引入任何明文身份字段（姓名/手机号/身份证/人脸） |

这不是风格偏好。"可信"二字既是产品唯一卖点，也是法律安全的基础。代码可以重构，红线不能重构。

## 1. 行为准则

- 对事不对人；尊重所有贡献者，无论其贡献大小；
- 不容忍骚扰、人身攻击、歧视性言论；
- 争议以技术论证与文档（PRD/SRS/技术白皮书）为裁决依据，不以声量定胜负；
- 严重违反者由维护者合议后封禁，不再另行警告。

## 2. 贡献方式

| 类型 | 说明 | 入口 |
|---|---|---|
| 代码 | 客户端 / 协议层 / AnchorBackend / Plaza 服务端 | PR |
| 安全研究 | 渗透测试、Vault/Plaza 隔离性验证 | 私密披露（见 §7） |
| 密码学审计 | SM2/SM3/SM4 实现规范性、Merkle 构造正确性 | 审计报告 issue |
| 法务审校 | 隐私政策、用户协议、机构合同模板的法律意见 | issue 标签 `legal` |
| 文档与翻译 | i18n、术语表、FAQ | PR |
| 设计 | 界面、公开页视觉（克制基线，无打分元素） | issue 标签 `design` |

**特别欢迎的方向**：Vault/Plaza 隔离性渗透测试报告；SM2/SM3/SM4 在各设备档位的性能基准；AnchorBackend 替代实现（天平链直连、社区节点）；隐私政策与用户协议的法律审校意见。

## 4. 分支与提交规范

**分支命名**：

    feat/<模块>-<简述>      新功能
    fix/<模块>-<简述>       缺陷修复
    security/<简述>         安全相关（敏感细节走私密披露，分支仅含修复）
    audit/<简述>            审计与测试
    docs/<简述>             文档

**提交信息**：遵循 Conventional Commits，扩展两类：

    feat: 新增双签邀请码一次性校验
    fix: 修复 Merkle proof 索引越界
    security: 升级依赖修复 CVE-XXXX-XXXX（细节见 docs/法律/安全.md 时间线）
    audit: 补充 PII 变体拦截测试集（T-03 扩充）
    docs: 补充锚定降级的 FAQ 条目

---

## 5. PR 流程

1. **PR 模板必填项**：勾选红线自查表（R1–R6）——未勾选的 PR 机器人自动挂起；
2. **评审**：一般变更 1 名维护者批准；涉及密码学路径（见 §6）需 2 名；
3. **门禁**：CI 必须通过——含可复现构建、SBOM 生成、PII 字段静态扫描（服务端 schema 禁出现明文身份字段是 CI 规则，不是人工约定）；
4. 合并采用 squash，保留完整 PR 讨论。

---

## 6. 密码学代码的特别流程

凡触碰以下文件/路径的变更，自动进入密码学评审通道：

- SM2/SM3/SM4 的调用封装、HMAC 构造、密钥派生；
- Merkle 树构建与证明生成；
- 序列化规范（canonical JSON）与哈希一致性校验；
- 安全芯片（Secure Enclave / StrongBox）交互层。

**硬性要求**：

- **禁止自研密码学原语**——只允许调用经审计的库；
- 必须附带国标测试向量（GB/T 32905-2016、GB/T 32918-2016、GB/T 32907-2016）的通过记录；
- 涉及签名/比较运算须考虑常量时间实现（时序侧信道）；
- 密码学路径必须附 fuzz 测试用例；
- 两名维护者复核，其中至少一人具备密码学工程背景。

## 7. 安全漏洞披露

- **不要在公开 issue 提交安全漏洞**；
- 发送至 `mengshulove@126.com`（PGP 公钥见 `docs/法律/安全.md`）；
- 协调披露窗口 90 天；
- 修复后报告摘要公开（不含利用细节）；
- 当前无现金赏金，致谢进 `docs/法律/安全.md` 荣誉榜。

**特别说明**：针对"Vault/Plaza 隔离性"的突破报告（渗透测试用例 T-02）属于最高优先级——这是本产品的一票否决项。

## 8. CLA

首次提交 PR 需签署 CLA（cla-assistant 自动引导）。CLA 为 MIT 友好型：你的贡献按 MIT 回馈项目，**你保留自己贡献的完整权利**。不接受 DCO sign-off 替代。
